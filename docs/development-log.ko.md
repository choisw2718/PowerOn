## body-3.5 네 바퀴 모델과 주행 기록

앞의 서보 두 개와 뒤의 모터·엔코더 두 개를 따로 계산하고, 조향 때의 타이어 돌출까지 포함해 벽 여유를 평가합니다. CAD에서 확인한 판은 150 × 200 mm입니다. 완성차의 후륜 윤거·바퀴 둘레·엔코더 분해능은 가상차 전용 가정을 따로 두었습니다. PC/Pi의 주행 판단과 가상 4륜 차량이 같은 스캔 유효시간, 정지거리, 명령 만료 검사를 사용합니다. [모델 가정과 실측 항목](../simulation/track/guide.ko.md#실차와-차이를-만드는-변수) · [조건별 시험](../simulation/benchmark/guide.ko.md)

노트북과 Pi에서 시작한 주행은 원본 회전 스캔, 명령·응답, 사용한 코드와 설정, 하드웨어 개정을 회차별로 남깁니다. 보관 중인 2026-11-11 COM19 캡처를 오프라인으로 재생해 완전한 29회전의 거리·각도·품질·시각 및 제어 출력을 원본과 대조했습니다. 이번 검증 범위는 소프트웨어와 기존 캡처 재생입니다. [기록·수거·비교](../vehicle/drive_data/guide.ko.md)

폭 56 cm 협로의 정상 조건에서 기존 경로 점수는 4회 모두 미완주했고 변경 후에는 4회 모두 완주했습니다. 최소 벽 여유는 8.33–8.84 cm로 기준 10 cm에 미달했습니다. 복합 고장에서는 4회 모두 충돌 없이 정지했습니다. 별도 주행 중 고장 시험에서 속도가 0.03 m/s 미만으로 떨어지는 데 0.930–1.080초가 걸렸습니다. 최종 전체 회귀 검사에서 Python 123개와 호스트 C++ 시험 프로그램 4개가 통과했습니다. [코스별 수치와 재현 명령](../simulation/benchmark/guide.ko.md#네-바퀴-모델-검증-결과)

## JGA25-370 듀얼 후륜 펌웨어와 벤치 명령

좌우 후륜 모터·엔코더를 독립 제어하는 모드를 추가했습니다. Nano가 엔코더 A/B 엣지를 받아 선속도를 추정하고, 조향 중심각과 후륜 윤거에서 계산한 바퀴별 목표에 맞춰 각 PWM을 조절합니다. 실측 프로필이 비어 있는 기본 빌드는 구동을 잠그고 엔코더 조회를 지원합니다. 중앙 후륜 코드는 모드 설정으로 복귀할 수 있습니다. 제조사 자료에 따른 기존 L298N의 벤치 사용 조건과 배선·보정 방법을 기록했습니다. [듀얼 후륜 안내](../vehicle/firmware/dual-rear.ko.md)

Arduino SAMD 1.8.14에서 양쪽 모드의 Nano 빌드에 성공했습니다. 호스트 C++에서 직선·좌우회전·후진의 후륜 목표, 속도 포화 시 좌우 비율, A/B 방향과 PI 제한을 검사했습니다. 보드 업로드와 실물 배선·구동 시험은 아직 하지 않았습니다.

## 라이다 순환 트랙 가상 시험

대형 순환 트랙에서 센서 누락, 전달 지연과 저접지를 반복하는 오프라인 시험을 제공합니다. 시드별 완주, 차체 여유, 관측 복구 대기와 Pi 명령 유효시간 부족을 비교합니다. 실제 TCP 재전송, Nano 응답 및 재연결 전체 순서는 이 가상 시험 범위 밖입니다. [스트레스 시험 실행](../simulation/benchmark/guide.ko.md#반복-스트레스-시험) · [공개 구현과 보완 순서](../lidar/autopilot/planning/track-planning.ko.md#공개-구현과-비교한-시뮬레이션-개선-순서)

가상 벤치마크에 `baseline`과 `scan-coast` 비교를 추가했습니다. `scan-coast`는 회전 스캔 도착이 늦으면 모터 출력을 0으로 낮추고, 새 경로 두 개의 정지거리와 명령 여유를 검사한 뒤 복귀합니다. [가상 주행 평가 기준](../simulation/benchmark/guide.ko.md#가상-주행-평가-기준)

헤어핀, 좁은 90° 코너, S자, 비대칭 벽과 벽 단절의 순환 코스를 추가했습니다. 화면에서 각 구간을 확인하고, 벤치마크에서 동일 조건을 여러 코스에 적용할 수 있습니다. [코스별 치수와 실행 방법](../simulation/track/guide.ko.md#코너별-순환-트랙)

순환 코스에서 체크포인트, 차량, 주행 궤적이 벽보다 왼쪽으로 밀리던 화면 좌표 오류를 수정했습니다. Tk 창의 기본 크기와 최소 크기에서 체크포인트가 있는 6개 코스의 결승선, 출발 위치와 이동 궤적이 맞는지 확인했습니다.

가상 코스의 구간별 벽 여유·기준 미달 시간과 정지 위치를 기록하고 `legacy`와 `clearance`를 같은 입력 조건에서 비교합니다. 정상 스캔에서 개선안은 헤어핀과 폭 0.56 m 코너를 세 시드로 통과했습니다. 좁은 코너의 복합 고장 조건은 미완주가 남아 있습니다. [경로 계획 비교](../simulation/benchmark/guide.ko.md#구간별-평가와-경로-계획-비교)

USB 수신을 경로 계산과 분리하고 표본 순서의 시각 추정과 회전 종료 좌표 보정을 연결했습니다. 가상 시험에 장착 진동, 거리 튐과 전방 거리·방향 오차를 추가했습니다. 실제 보정에는 스캔과 동기화한 차량 자세가 필요합니다. [움직이면서 측정한 스캔](../lidar/autopilot/guide.ko.md#움직이면서-측정한-스캔) · [가상 진동 시험](../simulation/track/guide.ko.md#진동과-거리-튐-시험)

## 2026-11-20 Pi 연결 및 최신 라이다 주행 코드 미리보기 확인

Raspberry Pi `andrea`에 SSH로 접속하고 CP210x 어댑터가 `/dev/ttyUSB0`으로 인식되는 것을 확인했습니다. 최신 주행 코드를 Pi의 `/home/user/poweron-lidar`에 설치하고 로컬과 파일 해시를 대조했습니다. Pi에서 계산 전용으로 6초 실행해 스캔 **36회**를 처리했습니다. 당시 배치에서는 전진 여유가 부족해 36회 모두 PWM 0%였습니다. Nano 업로드와 차량 구동은 진행하지 않았습니다.

## 2026-11-19 라이다 재연결 변경 후 SSH 복구 확인

Raspberry Pi의 실제 라이다를 Windows 레이더 수집 코드로 읽는 중 시험용 SSH 세션을 한 차례 종료했습니다. 종료 전 유효값 6,902개를 수신했고, 2초 재시도 상태가 표시된 뒤 새 SSH 연결에서 유효값 3,000개를 수신했습니다. Windows USB 포트 번호 변경과 자율주행 세션 종료 후 계산 전용으로 재연결하는 흐름은 모의 시험에서 확인했습니다. 이 시험에서 차량에 접속하지 않았습니다.

## 2026-11-19 Pi 라이다 벽 추종 계산 확인

RPLIDAR A1M8-R5를 Raspberry Pi 4B에 USB로 연결한 상태에서 새 벽 추종 프로그램의 계산 전용 모드를 5초 실행했습니다. 완전한 스캔 **30회**를 처리했습니다. 당시 배치에서는 정지에 필요한 전진 거리를 확인할 수 없어 30회 모두 **PWM 0%**를 계산했습니다. 이 시험에서 Nano에 접속하거나 움직임 명령을 보내지 않았습니다.

모의 트랙에서 중앙 복귀, 좌우 코너 판단, 연속 스캔으로 우측 90° 코너 통과, 막힌 길과 전방 관측 누락의 정지를 확인했습니다. 명령 테스트에서 오래된 스캔으로 출발하거나 전진하지 않는 것을 확인했습니다. Nano용 새 스케치는 컴파일했고 전체 Python 테스트 24개와 기존 C++ 테스트를 통과했습니다. Nano 업로드, 실차 조향·정지거리 보정, 실제 트랙 주행은 다음 검증 단계입니다. [실행 및 보정 절차](../lidar/autopilot/guide.ko.md)

## 2026-11-19 라이다 SSH 자동 복구와 연속 수신 확인

Windows 레이더 수집 작업에서 Raspberry Pi 4B와 RPLIDAR A1M8-R5의 표준 스캔을 받는 중 SSH 세션을 한 차례 종료했습니다. 레이더는 연결 중단을 표시하고 자동으로 다시 연결했습니다. 복구 후 **120초 동안 패킷 239,995개와 유효값 188,435개**를 수신했습니다. 이 구간에서 추가 재연결은 없었고, 시험 종료 시 수집 작업이 끝나는 것을 확인했습니다. 이번 시험 범위는 SSH 세션 중단 복구와 복구 후 2분 연속 수신입니다.

## 2026-11-19 Windows 레이더에서 Raspberry Pi SSH 실수신 확인

RPLIDAR A1M8-R5를 Raspberry Pi 4B의 `/dev/ttyUSB0`에 연결한 상태에서 Windows 레이더의 `Raspberry Pi (SSH)` 모드를 시험했습니다. `andrea.local`을 통해 115200bps 표준 스캔을 받았습니다. 첫 표시 확인 시 **7,789개 패킷, 유효값 5,765개, 녹색 점 521개**였습니다.

정지 후 수집 작업이 종료되고 수신 숫자가 유지되는 것을 확인했습니다. 같은 포트에서 다시 시작해 **7,351개 패킷, 유효값 5,478개, 녹색 점 512개**를 확인했습니다. **SSH를 통한 실시간 표시와 정지·재시작을 확인했습니다.** 표시 점 수는 확인 시점의 레이더 화면에 그려진 점을 집계한 값입니다.

## 2026-11-19 Raspberry Pi 4B에서 USB 라이다 수집 확인

Windows PC에서 Raspberry Pi 4 Model B Rev 1.4에 유선 SSH로 로그인했습니다. Pi에 저장된 Wi-Fi 프로필의 SSID 대소문자가 실제 네트워크 이름과 달라, 실제 SSID로 새 연결을 만들어 `wlan0`에서 IPv4 주소를 받는 것을 확인했습니다.

Pi의 `cp210x` 드라이버가 RPLIDAR USB 어댑터를 `/dev/ttyUSB0`에 연결하는 것을 확인했습니다. 연결이 한 차례 끊긴 뒤 어댑터 인식이 복구된 상태에서 기존 `build/capture_lidar.py`로 115200bps 표준 스캔을 실행했습니다. **5.001초 동안 9,355개 패킷, 유효 거리값 7,132개, 회전 시작 표식 30개**를 수신했습니다. 파싱 중 버린 바이트와 종료 시 잔여 바이트는 각각 0개입니다. 유효 반환 거리는 142.0~2,703.5mm였습니다. CSV·원시 바이트·요약은 이번 시험의 Pi 임시 폴더에 저장했습니다. **Pi의 USB 시리얼 통신과 거리·각도 실수신을 확인했습니다.** 거리 정확도와 장시간 USB 연결 안정성은 별도 시험이 필요합니다.

## 2026-11-11 USB 라이다 레이더 화면 실제 수신 확인

`lidar_radar.py`와 `run_lidar_radar.cmd`를 추가했습니다. RPLIDAR A1 표준 스캔을 COM19/115200bps로 수신해 센서 기준 각도·거리의 녹색 점, 거리 눈금, 최신 스캔 방향 선과 누적 수신 수를 표시합니다. 최근 1초 값만 유지하며 거리/quality가 0인 반환은 점에서 제외합니다. 포트 입력, 시작·정지, 표시 반경 선택을 제공합니다. 수집은 별도 스레드, 화면은 50ms 주기로 갱신하며 종료 시 STOP 후 포트를 해제합니다. 이 화면은 CSV 저장이나 차량 제어를 수행하지 않습니다.

문법 검사 및 실제 GUI 8초 실행에서 **14,612개 패킷, 유효값 11,069개** 수신 후 정상 종료를 확인했습니다. 이어 실제 Windows 창에서 녹색 거리점·눈금·COM19 수신 상태와 정지 버튼의 포트 해제·재시작 조작을 확인했습니다. 기본 창 크기는 화면에 맞춰 760×760으로 조정했습니다. 거리 정확도·물리 장착 방향·차량 연동 검증은 포함하지 않습니다.

## 2026-11-11 RPLIDAR A1M8-R5 USB 거리 데이터 수집 확인

사용자가 SLAMTEC RPLIDAR A1M8-R5를 PC에 USB로 연결하고 회전 중임을 확인했습니다. CP2102 드라이버 미설치(오류 코드 28) 상태 이후 재조회에서 **Silicon Labs CP210x USB to UART Bridge(COM19), 상태 OK**를 확인했습니다. 115200bps 장치 정보 응답은 펌웨어 **1.25**, 하드웨어 **5**, health **0**, 오류 코드 **0**이었습니다.

`build/capture_lidar.py --port COM19 --seconds 5`로 표준 스캔을 실제 수집했습니다. **5.000초, 9,352개 패킷, 유효 거리값 6,833개, 회전 시작 표식 30개**였으며 파싱 중 버린 바이트는 0개, 종료 시 불완전 패킷 잔여는 3바이트였습니다. 유효 기준은 거리와 quality가 모두 0보다 큰 값입니다. 유효 반환 거리는 **144.5~3,606.0mm**, 각도는 센서 기준 **0.03125~359.953125°**였습니다. 이 범위는 당시 주변 물체의 반환값이며 제조사 측정 범위나 실제 거리 정확도 검증을 뜻하지 않습니다.

CSV·원시 수신 바이트·요약은 `build/lidar_captures/20261111_154213/`에 저장했습니다. CSV의 시간은 PC 수신 시각의 경과 시간이며 하드웨어 표본 시각이 아닙니다. 거리 0 또는 quality 0인 반환도 CSV에 남기고 valid=0으로 구분합니다. 수집 종료 시 스캔 STOP 후 포트를 닫았습니다. **USB 통신과 거리 데이터 수집 확인 완료**이며, 센서 장착 방향·기준 물체 거리 정확도·SLAM·차량 제어 연동은 미검증입니다. Nano 펌웨어·기존 SHARP 센서 설정은 수정하지 않았고 차량 구동 명령도 전송하지 않았습니다.

## 2026-11-11 별도 5V·20cm 기준 물체 확인, 부트로더 상태 복구 대기

사용자는 오른쪽 센서 전원을 **별도 5V와 공통 GND**에 연결했고 정면 **약 20cm에 기준 물체**를 놓았다고 확인했습니다. 실제 전압은 멀티미터가 없어 측정하지 못했습니다. A2만 활성화·분압비 1.0인 현재 소스를 확인했습니다.

기준 ADC 수집을 시도했으나 UDP 검색은 무응답이었고, 기존 주소 192.168.50.223:5000의 TCP 연결 후에도 Nano READY 배너가 오지 않았습니다. Windows에서 **Arduino NANO 33 IoT bootloader(COM8), VID_2341/PID_0057**을 확인했습니다. PC Wi-Fi는 poweron에 연결되어 있었고, COM8/115200 읽기에서는 USB 진단 출력이 없었습니다. 현재 사용자 스케치가 정상 실행 중인 것으로 확인되지 않아 **20cm 기준 샘플은 아직 수집하지 못했습니다.**

현재 소스는 컴파일에 성공했습니다(Flash **61,388 바이트**, RAM **4,936 바이트**). COM8에 업로드를 시도했지만 bossac가 장치 식별·전송을 시작하지 못한 채 대기했습니다. 해당 작업의 bossac 프로세스에서 읽기/쓰기 전송 바이트가 모두 0임을 확인한 뒤 그 프로세스만 종료해 포트를 해제했습니다. 이 시도는 **업로드 성공으로 기록하지 않습니다.** 사용자가 RESET을 한 번 눌러 기존 센서 스케치의 정상 실행으로 돌아오도록 요청했습니다. 임의 거리 보정이나 주행 명령은 수행하지 않았습니다.

## 2026-11-10 직결 상태 재조회와 전원·기준거리 확인 대기

사용자는 멀티미터가 없으며 저항 없이 조정 가능한지 먼저 확인하고, 불가능하면 배선 방법을 안내해 달라고 요청했습니다. 현 펌웨어의 분압비 1.0과 A2만 활성화된 설정을 확인했습니다. 코드를 다시 바꾸지 않은 상태로 실제 조회 3초/6회를 수행하자 A2는 ADC **236~418**, 명목 약 **0.190~0.337V**, `far_or_unknown`으로 돌아왔습니다. A0/A1은 모두 `not_connected`였습니다. 이전 ADC 4095 포화가 이번 조회에서는 재현되지 않았지만 그 원인은 아직 확인하지 못했습니다.

사용자가 오른쪽 센서는 열린 공간을 보고 있다고 했으므로 저출력만으로 거리 환산식을 추가 조정하지 않습니다. 센서 Vcc/GND의 연결 위치와 정면 20cm 기준 물체에서의 ADC 반응을 요청했습니다. 값이 없으므로 센서 전원 정상·직결 안전·실제 거리 정확도는 검증 완료로 표시하지 않습니다. 멀티미터 없이 기준 물체로 확인하는 절차와 필요 시 10kΩ/10kΩ 분압 배선을 [센서 안내](../vehicle/sensor_monitor/guide.ko.md)에 추가했습니다. 이번 재조회에서는 펌웨어 변경·재업로드·구동 명령을 수행하지 않았습니다.

## 2026-11-10 A2 한 개 연결 확인과 미연결 채널 제외

사용자는 **오른쪽 센서만 A2에 연결되어 있고 열린 공간을 보고 있다**고 추가 확인했습니다. 따라서 앞서 A0/A1에서 읽어 환산한 약 20cm는 실제 센서 거리값이 아니며 유효한 거리 검증 결과로 사용할 수 없습니다. 기존의 단순 ADC 응답 확인과 물리 센서 값 확인을 구분합니다.

`kDistanceSensorConnected={false,false,true}`를 추가해 A0/A1은 ADC를 읽지 않고 `not_connected`/사용 불가로 처리합니다. PowerShell에는 ADC·전압·거리를 모두 `--`로 표시합니다. 나중에 센서를 연결하면 해당 플래그를 true로 수정해야 합니다. 주행은 계속 비활성이며 세 유효 센서 입력이 없는 상태에서는 시작하지 않습니다. 사용자는 직결 배선을 확인했으므로 분압비 1.0은 유지합니다.

C++ 검사에서 미연결 핀을 읽지 않는 것과 오류 입력 처리를 확인했고 Python **18건**을 통과했습니다. 최종 스케치 컴파일(Flash **61,388 바이트**, RAM **4,936 바이트**)과 COM6 업로드·체크섬 검증을 완료했습니다. 재업로드 후 실제 조회 2초/4회에서 A0/A1의 `not_connected` 표시를 확인했습니다. 그러나 **A2는 네 번 모두 ADC 4095, 표기 3.300V, `signal_fault`**로 포화됐습니다. 앞선 낮은 출력과 달라진 원인은 아직 확인하지 못했으며 정상 거리 측정으로 기록하지 않습니다. ADC 상한 표시는 실제 전압이 정확히 3.300V라는 뜻이 아니고 초과 여부도 구분하지 못합니다. A2에서 신호선을 분리하고 센서 Vcc–GND / Vo–GND 전압을 확인하도록 요청했으며 물리 전압 확인이 남아 있습니다. 모터 구동·자율주행 시작은 수행하지 않았습니다.

## 2026-11-10 사용자 확인 직결 배선으로 거리 환산 수정

값이 이상하다는 사용자 보고 후 확인한 결과, **센서 Vo를 A0/A1/A2에 직접 연결했고 분압기는 없었습니다.** 이전 코드는 배선을 확인하기 전에 10kΩ/10kΩ 분압비 0.5를 가정해 센서 Vo를 ADC 핀 전압의 2배로 계산했습니다. 실제 ADC 약 1600에서 약 1.29V를 2.58V로 환산하여 `too_near`로 분류하는 오류가 있었습니다. 현재 기본 `dividerRatio`를 **1.0**으로 수정했습니다. 센서별 실제 거리 보정은 별도이며 곡선 자체를 측정 없이 바꾸지 않았습니다.

`SENSORS` 응답과 PowerShell 표에 ADC 핀 전압·적용 분압비·센서 Vo를 구분해 표시하도록 보완했습니다. 직결이면 두 전압이 같으며 분압비가 1.000으로 표시됩니다. 이전 펌웨어의 분압비가 보고되지 않으면 모니터는 임의 가정하지 않고 `unknown`으로 표시합니다. 이 환산 설정은 입력 과전압을 보호하는 회로 기능이 아닙니다.

PC 검사에서 ADC 1600/직결 1.0과 ADC 800/분압 0.5가 동일한 약 1.29V·20cm로 변환됨을 확인했고, C++ 시나리오 및 Python **17건**을 통과했습니다. Arduino SAMD 1.8.14 환경에서 컴파일했고(Flash **61,336 바이트**, RAM **4,932 바이트**), COM6에 재업로드해 플래시 체크섬 검증 성공을 확인했습니다. 모터 전원 꺼짐이라는 앞선 사용자 확인 조건을 유지하며, 자율주행 출력은 계속 비활성입니다.

실제 Wi-Fi 조회 3초/6회에서 세 채널 분압비 **1.000**, ADC 핀 전압과 센서 Vo가 동일하게 표시되는 것을 확인했습니다. 왼쪽 ADC **1457~1586**, 약 **1.174~1.278V / 20.4~22.7cm**, 전방 ADC **1401~1637**, 약 **1.129~1.319V / 19.6~23.9cm**로 모두 `in_range`였습니다. 오른쪽 ADC **233~465**, 약 **0.188~0.375V**는 계속 `far_or_unknown`이었습니다. **실제 물체 거리를 측정해 일치시킨 시험은 아니며**, 오른쪽의 원거리/반사/연결 상태와 센서 전원 등은 추가 확인이 필요합니다. 실제 거리 보정·주행 성공으로 기록하지 않습니다. 아래의 0.5 설정 시험값은 수정 전 이력으로 남깁니다.

## 2026-11-10 센서 펌웨어 업로드와 실제 ADC 수신

사용자가 USB 연결과 모터 전원 꺼짐을 확인했습니다. 처음에는 Windows 시리얼 포트와 Arduino USB 장치가 보이지 않았으나, 사용자가 RESET을 빠르게 두 번 누른 뒤 **Arduino NANO 33 IoT(COM6), USB VID_2341/PID_8057**을 확인했습니다. 현재 메인 스케치를 Arduino SAMD 1.8.14 환경에서 컴파일했고(Flash **61,184 바이트**, RAM **4,932 바이트**), COM6에 업로드해 **Verify successful**과 CPU reset을 확인했습니다. 자율주행 출력 설정은 계속 비활성입니다.

같은 Wi-Fi에서 **192.168.50.223:5000**에 연결해 `STOP` 후 3초간 `SENSORS`를 조회했습니다. 실제 응답 6회에서 `available=1`, 표본 나이 17~60ms를 확인했습니다. ADC 범위는 왼쪽 A0 **1410~1607**, 전방 A1 **1526~1652**, 오른쪽 A2 **229~452**였습니다. 현재 임시 표·분압비 0.5 설정에서는 왼쪽이 주로 `too_near`(1회 `in_range` 약 10.1cm), 전방은 `too_near`, 오른쪽은 주로 `far_or_unknown`(1회 `in_range` 약 39.4cm)으로 분류됐습니다. 이는 ADC와 통신 응답 확인이며 **실제 벽 거리, 센서별 보정, 실물 분압기·전원 구성, 물리적 좌우 대응을 검증한 결과가 아닙니다.** 표시 전압도 ADC/설정 분압비로 역산한 값입니다.

조회 완료 후 연속 표시용 PowerShell에서 `run_sensor_monitor.ps1 -NanoHost 192.168.50.223`을 실행했습니다. 기본 간격은 0.5초이고 Ctrl+C로 종료합니다. 모터 구동·자율주행 시작 명령·실물 조향 시험은 수행하지 않았으며 기존 부팅/접속/종료의 서보 중앙 명령은 적용됩니다. 이전의 USB 미감지·센서 명령 미지원 기록은 당시 이력으로 남깁니다.

## 숫자 키로 자율주행·수동 전환 (소프트웨어 검증)

`wifi_control.py` 일반 키보드 조종기에 `1 → AUTO START`, `0 → IDLE`을 추가했습니다. `0`은 자율주행을 취소하고 모터 정지·조향 중앙 후 기존 W/S/A/D 수동 제어로 복귀합니다. 두 전환 모두 Python의 수동 속도·조향 기억값을 0으로 초기화해 과거 입력이 다음 수동 명령에서 되살아나지 않게 했습니다. 기존 G/I 및 정지 키도 유지합니다. `--sensors` 조회 전용 모드에서는 숫자 키를 처리하지 않습니다.

모드 전환·과거 수동 값 초기화·수동 재조종·기존 단축키 유지 검사 4건을 추가했고 전체 Python 검사 **15건**과 문법·공백 검사를 통과했습니다. 펌웨어는 이번 키 추가에서 변경하지 않았으며 기존 주행 비활성 설정과 센서 검사는 유지합니다. 실제 주행 시작에는 현재 펌웨어 업로드·활성화와 정상 센서 입력이 필요합니다. 이번 검증에서 장치 접속·업로드·실물 주행은 수행하지 않았습니다.

## PowerShell 센서 연속 모니터

`wifi_control.py --sensors`와 `run_sensor_monitor.ps1`을 추가했습니다. UDP 검색 또는 지정한 IP로 연결해 0.5초마다 세 센서의 ADC·전압·거리(cm)·상태·사용 가능 여부를 표시합니다. 범위 밖 거리는 실측값으로 표시하지 않습니다. 시작 시 STOP과 센서 조회만 보내며 종료 시 기존 IDLE 처리를 적용합니다. `--sensor-interval`과 `--sensor-duration`으로 조회 간격·실행 시간을 지정합니다. 주행 명령은 전송하지 않습니다.

Python 검사 11건으로 세 채널 표시, 단위 변환, 범위 밖 표시, TCP 응답 분할 수신, 이전 펌웨어 오류 안내, 연결 해제를 확인했습니다. C++/펌웨어는 이번 모니터 추가에서 변경하지 않았습니다.

**2026-11-10 실제 연결 확인:** UDP로 Nano **192.168.50.223**을 발견하고 TCP 접속에 성공했습니다. 시작 STOP 후 `SENSORS` 조회에는 **`ERR bad command; send HELP`**가 반환되어 실행 중인 펌웨어에 센서 조회 기능이 없음을 확인했습니다. 같은 시점 `arduino-cli board list`는 **No boards found**를 반환했습니다. 센서 값 취득·센서 보정·펌웨어 업로드·실물 주행은 수행하지 않았습니다. 센서 값을 표시하려면 USB 연결 후 현재 스케치를 업로드해야 합니다.

## SHARP GP2Y0A21YK0F 확정과 소수 각도 조향 보완 (소프트웨어 검증)

사용자가 거리 센서를 **SHARP GP2Y0A21YK0F 3개**로 확정했습니다. `DistanceSensors.h`에 왼쪽 A0 / 전방 A1 / 오른쪽 A2, 12비트 ADC, 200ms 준비 시간, 60ms 읽기 주기, 채널 전환 첫 값 폐기와 5개 ADC 중앙값을 구현했습니다. 센서는 별도 5V 공급과 각 Vo의 10kΩ/10kΩ 분압기를 가정합니다. `SharpIr.h`의 전압-역거리 변환 표는 [SHARP 제조사 곡선](https://global.sharp/products/device/lineup/data/pdf/datasheet/gp2y0a21yk_e.pdf)을 대략 읽은 임시값이며 센서별 실측 보정은 미완료입니다.

주행 입력 범위와 CSV를 100~800mm로 바꾸고 임시 정지 기준을 전방 150mm / 좌우 120mm로 옮겼습니다. 낮은 출력은 `far_or_unknown`으로 분리하며 기본적으로 주행에 사용하지 않습니다. 긴 직선에서는 실물 확인 후 센서별 `allowLowSignalAsFar` 정책 결정이 필요합니다. 이를 허용해도 원거리와 오류를 구별할 수 없고, 10cm 이내 출력의 비단조성도 남습니다. `SENSORS` 명령과 Python `L` 키로 ADC·전압·추정 거리·상태·사용 가능 여부를 조회하도록 했습니다. 배선과 보정 절차는 [센서 안내](../vehicle/sensor_monitor/guide.ko.md)에 있습니다.

자율주행 조향은 키보드 2° 단계와 별도로 소수 각도를 계산하고, 기존 1µs 정수 펄스 출력을 유지합니다. 명목 10µs/° 기준 약 0.1° 바퀴 각도 명령 분해능이며 기계적 정밀도 측정은 아닙니다. `AutonomousSteering.h`로 20ms/50Hz 출력과 직선 20°/s, 회전 진입·정렬 90°/s 변화율을 적용했습니다. 회전 진입의 명령 각도가 준비될 때까지 모터 목표를 0으로 유지하며, 코너 후 큰 조향각이 남으면 낮은 PWM 정렬 상태를 유지합니다. 실제 서보 위치 피드백은 없습니다. `AUTO STATUS`에는 원래 목표와 보간 각도를 구분해 표시합니다.

호스트 C++ 검사에서 비선형 환산·분압비·범위 밖 정책, ADC 준비 시간·채널 전환·중앙값·오류 표본 갱신, 소수 각도·시간 지연 상한·millis 순환 및 기존 직선/코너/정지 시나리오를 통과했습니다. Python 검사 5건도 통과했습니다. ## body-2 도면 기반 애커만 조향 수정 (소프트웨어 검증)

사용자가 `body-2 Drawing.pdf`를 현재 설계도로 제공했고, 앞쪽 서보에 약 40 mm 막대를 통해 연결된 바퀴가 막대와 함께 회전하며 서보 모델은 **Hitec HS-311**이라고 확인했습니다. 중립은 잘 맞지만 큰 조향 명령에서 slip이 의심된다는 보고입니다. 이번 수정은 계산·컴파일 검증이며 재업로드나 새 실물 시험을 뜻하지 않습니다.

기존 코드에도 애커만 계산은 있었지만 Uno에서 가져온 축간거리 215 mm / 간격 188 mm를 사용했습니다. 이를 도면과 [HS-311 제조사 치수 도면](https://www.hiteccs.com/public/uploads/data_sheet/HCS_HS-311_Specsheetv2.2_102-1729889658.pdf)에 따른 **축간거리 약 133.24 mm / 조향 회전축 간격 약 121.20 mm**로 변경했습니다. 이 값은 조립체 실측값이 아닌 아래 가정에 따른 명목값입니다. `STATUS geometry=body2-hs311-nominal`로 구분합니다.

- 도면 아래쪽이 전방이며, 위쪽 중앙의 길쭉한 구멍이 후륜 자리이고 후륜 회전축은 그 구멍의 길이 방향 중앙에 있다고 가정합니다. 전방 모서리에서 후륜 축까지는 도면의 109.01 mm에 PDF 형상에서 판독한 구멍 길이 약 75 mm의 절반을 더한 **146.51 mm**입니다.
- 앞 서보 축은 도면의 장착 구멍 두 줄 사이 중앙에 있다고 봅니다. 구멍 한 줄의 전방 모서리 기준 위치 18.27 mm에서 PDF 형상의 두 줄 간격 약 10 mm의 절반을 빼면 **13.27 mm**입니다. 축간거리는 146.51 - 13.27 = **133.24 mm**입니다.
- 두 서보의 출력축이 각각 바깥쪽을 향한다는 기존 배치 설명을 따릅니다. 바깥 장착 구멍 열의 위치는 차체 왼쪽 기준 약 6.83 / 155.83 mm이며, HS-311 출력축은 바깥 구멍 열에서 안쪽으로 13.9 mm 떨어져 있습니다. 회전축 간격은 155.83 - 6.83 - 2×13.9 = **121.20 mm**입니다. 6.83 mm, 구멍 길이 75 mm와 두 줄 간격 10 mm는 PDF 형상에서 판독한 근삿값이며 별도 기입 치수가 아닙니다.
- 막대가 직진 상태에서 좌우 바깥 방향이고 바퀴 축과 나란하며, 서보축 대비 바퀴 중심의 전후 오프셋이 없다고 가정합니다. 이런 강체 구조에서는 막대 길이 40 mm가 바퀴 위치에는 영향을 주지만 횡방향 무미끄럼 조건에서 소거됩니다. 따라서 40 mm를 조향각 배율로 적용하거나 바퀴 중심 간격 약 201.20 mm를 회전축 간격으로 사용하지 않습니다. 전후 오프셋이 있으면 이 모델을 다시 수정해야 합니다.

중심 조향각 δ에서 후륜 축 위의 회전 중심까지 거리 R = L / tan(|δ|)를 구하고, 좌우 서보축 간격 T를 사용해 안쪽 바퀴 각도 atan(L / (R - T/2)), 바깥쪽 바퀴 각도 atan(L / (R + T/2))를 계산합니다. 양수는 좌회전입니다. 좌회전 +30°의 계산값은 왼쪽 +38.059° / 오른쪽 +24.573°이며, 우회전 -30°는 왼쪽 -24.573° / 오른쪽 -38.059°입니다. 이는 목표 각도이며 실측 바퀴 각도가 아닙니다.

기존에는 펄스 상하한에서 한 채널만 잘릴 수 있었습니다. 이제 중립·방향·채널별 µs/°·펄스 한계·바퀴 각도 한계로 각 바퀴의 허용 범위를 먼저 계산하고, **안쪽과 바깥쪽 바퀴 중 어느 쪽이 먼저 한계에 도달하든 공통 회전 반경을 제한**합니다. 한쪽 각도만 잘라 애커만 관계를 깨지 않습니다. 마지막 펄스 제한은 반올림과 수치 오차를 위한 방어 처리로 유지합니다. 현재 중심 조향 계산 범위는 약 **-34.50°~+39.99°**이며, 조종기의 ±30° 범위는 그대로입니다. 기구의 실제 안전 한계가 측정됐다는 의미는 아닙니다.

중립 **D5=1597 µs / D6=1416 µs**, 방향 **+1/+1**, 기존 교차 채널 대응과 펄스 상하한은 유지했습니다. HS-311의 명목 10 µs/°도 유지하되, 향후 실측 보정을 위해 D5/D6 상수를 분리했습니다. `STATUS`에 요청/적용 중심 각도, 좌우 목표 각도, 조향 제한 여부, 기하 설정과 유효 중심 각도 한계를 추가했고 버전은 `steering_cal=ackermann-body2-v4`입니다. Python은 기존 명령 형식을 유지하고 각도 표시의 의미와 상태 확인 안내만 보완했습니다.

Arduino SAMD 1.8.14 / Servo 1.3.0 / WiFiNINA 2.1.1 / Arduino_SpiNINA 0.0.2 환경에서 컴파일에 성공했습니다(Flash **54,252 바이트**, RAM **4,564 바이트**). 별도 수치 계산 160,032건으로 방향 부호·교차 대응 조합, 중립 유지, 펄스 범위와 큰 명령 제한을 확인하고 40 mm 강체 막대 끝의 바퀴 중심에서 독립적인 횡방향 무미끄럼 조건을 검증했습니다. 이는 펌웨어의 실물 실행 시험이 아닙니다. 계산상 기존과 새 L/T 비율 차이는 작으므로 이번 변경만으로 slip 제거를 단정하지 않습니다. 실제 축 위치, D5/D6의 바퀴 대응, 명령 대비 실측 바퀴 각도와 지면 주행은 아직 확인하지 않았습니다. 아래 과거 실물 시험 기록·날짜·완료 표시는 갱신하지 않습니다.

## 2026-10-08 중립 성공 보고와 왼쪽 서보 방향 반전

사용자가 2차 보정 후 중립 상태가 아주 잘 맞는다고 보고했고, 이 중립을 유지한 채 왼쪽 서보의 회전 방향만 반대로 바꾸도록 요청했습니다. 정확한 시험 명령과 STATUS 로그는 제공되지 않았으며, 중립 성공은 사용자 보고로 기록합니다.

현재 교차 채널 설정에서 물리적 왼쪽을 제어하는 **D6의 방향만 -1→+1**로 변경했습니다. 오른쪽 D5의 방향은 +1이며, 중립 **D5=1597 µs / D6=1416 µs**, 채널 대응, 바퀴별 각도 계산과 펄스 상하한은 그대로 유지합니다. 같은 비영점 바퀴 각도에서 D6의 펄스 변화 방향만 반전되고 조향 0°의 출력은 같습니다. 거울 배치만으로 방향 부호를 강제하던 검사는 제거하고 각 채널의 방향이 ±1인지 검사하도록 수정했습니다. STATUS 버전은 `steering_cal=neutral-v3`입니다.

이번 방향 변경은 Arduino SAMD 1.8.14 / Servo 1.3.0 / WiFiNINA 2.1.1 / Arduino_SpiNINA 0.0.2로 컴파일에 성공했습니다(Flash 53,412 바이트, RAM 4,560 바이트). 계산 검증에서 조향 0°의 중립 펄스와 오른쪽 D5 출력을 유지하면서 ±5°에서 왼쪽 D6의 펄스 변화만 반전됨을 확인했습니다. 재업로드와 실물 회전 방향은 아직 검증하지 않았습니다. 사용자 보고로 확인된 것은 기존 2차 중립이며, 방향 변경 후 작은 좌·우 조향과 기구 한계는 별도 확인 항목입니다.

## 2026-10-08 거울 배치와 2차 정렬 관찰을 반영한 조향 보정 (이전 기록)

사용자는 1차 보정 스케치(D5 중립 1378 µs, D6 중립 1663 µs)를 실제로 업로드했다고 확인했습니다. 이 상태에서 모터 명목 명령 0 V로 오른쪽 바퀴는 `DRIVE 0.0 26.0`, 왼쪽 바퀴는 `DRIVE 0.0 -30.0`에서 정렬된다고 보고했고, 두 서보가 서로 바깥 방향으로 거울 대칭 배치라고 설명했습니다. 실제 D5/D6의 물리적 좌우 연결과 각 측정 위치의 STATUS 응답은 아직 받지 않았습니다.

1차 펌웨어의 기존 계산으로 두 관찰을 펄스로 환산했습니다. +26°의 D5/D6 출력은 **1597/1952 µs**, -30°의 출력은 **1001/1416 µs**입니다. +26°에서 D6는 1952 µs 상한에 포화되므로 그 위치의 표시 각도를 D6 중립으로 직접 사용해서는 안 됩니다. 기존 교차 채널 설정(D5→물리적 오른쪽, D6→물리적 왼쪽)을 유지하는 가정으로 각 바퀴가 정렬된 채널의 펄스를 선택해 새 중립을 **D5=1597 µs / D6=1416 µs**로 반영했습니다. 이 값은 계산 결과이며 STATUS 실측이나 보정 후 두 바퀴 동시 정렬을 확인한 값은 아닙니다.

거울 배치는 중립과 별도로 처리합니다. 조향 각도의 펄스 변환 방향을 **D5=+1 / D6=-1**로 분리하여 같은 방향의 바퀴 각도에 두 채널의 펄스가 서로 반대로 변합니다. 전체 조향 좌우 방향은 작은 입력으로 재확인해야 합니다. 중립 관찰 펄스는 새 방향 부호를 적용하기 전 펌웨어에서 계산했으며, 중립에 다시 각도 오프셋을 더하거나 빼지 않습니다. 기존 펄스 상하한은 유지하고, 중립이 상하한에 걸리거나 방향 부호가 같으면 컴파일에서 거부합니다.

`STATUS`에 `steering_cal=mirror-v2`, 두 채널의 중립·방향·교차 설정과 `pulse_limit_d5/d6`를 추가했습니다. 보정 후 조향 0°의 예상 출력은 `servo_us_l=1597 servo_us_r=1416`입니다. Arduino SAMD 1.8.14 / Servo 1.3.0 / WiFiNINA 2.1.1 / Arduino_SpiNINA 0.0.2로 컴파일에 성공했습니다(Flash 53,420 바이트, RAM 4,560 바이트). 계산 검증에서 1차 펌웨어 관찰 명령의 펄스 환산, 새 중립 출력, ±5°에서 펄스 변화 방향과 키보드 -30~+30° 구간의 펄스 상하한 유지를 확인했습니다. 물리적 채널 대응, 재업로드, 두 바퀴 동시 중립·작은 좌우 조향·기구 한계는 아직 검증하지 않았습니다. 아래 1차 보정값은 이 2차 보정으로 대체합니다.

## 2026-10-08 사용자 측정에 따른 1차 조향 중립 보정 (이전 기록)

사용자는 기존 조종기의 `DRIVE 0.0 22.0`에서 물리적 왼쪽 바퀴가 중립이고, `DRIVE 0.0 -2.0`에서 물리적 오른쪽 바퀴가 중립이라고 보고했습니다. 두 측정의 모터 명목 명령은 0 V입니다. 측정 기준은 변경 전 메인 스케치의 중앙 펄스 D5=1398 µs / D6=1402 µs와 기존 교차 채널 설정(`kServoChannelsCrossed=true`, D5→물리적 오른쪽, D6→물리적 왼쪽)입니다.

기존 바퀴별 각도 계산을 적용하면 중앙 조향 +22°에서 왼쪽 바퀴 계산 각도는 약 +26.1375°이고 D6 펄스는 1663 µs입니다. 중앙 조향 -2°에서 오른쪽 바퀴 계산 각도는 약 -2.0310°이고 D5 펄스는 1378 µs입니다. 이 두 펄스를 새 중립값으로 반영하여 `CENTER`, `IDLE`, 부팅·접속·연결 해제의 조향 0°가 D5=1378 µs / D6=1663 µs를 출력하게 했습니다. Python의 조향 명령 0°는 그대로 사용합니다.

기존 펄스 범위 D5=948~1948 µs / D6=952~1952 µs는 유지했습니다. Arduino SAMD 1.8.14 / Servo 1.3.0 / WiFiNINA 2.1.1 / Arduino_SpiNINA 0.0.2로 컴파일에 성공했고(Flash 53,060 바이트, RAM 4,560 바이트), 관찰 명령의 계산 펄스와 1차 중립값 일치 및 펄스 상하한 유지를 확인했습니다. 이 작업 당시에는 USB 보드가 감지되지 않아 업로드하지 않았으며, 이후 사용자가 직접 업로드했다고 확인했습니다. 물리적 채널 대응을 확인하지 않은 가정과 같은 방향 부호를 사용한 1차 보정에서 두 바퀴 동시 중립은 검증하지 못했습니다. 이 값은 위 2차 보정으로 대체합니다.

## 2026-10-08 연결·실행 준비 확인

실제 PC 환경에서 USB **Nano 33 IoT(COM6)**, PC Wi-Fi와 로컬 설정 SSID **poweron**, UDP 검색 응답 **192.168.50.222**를 확인했습니다. TCP 5000에서 `READY`, `STATUS`, `NETWORK`, `STOP` 응답을 받았으며, 실행 중 펌웨어는 `driver=L298N channel=A`, 정지 명령 상태는 `duty_cmd=0.0% duty_applied=0.0% enabled=0`이었습니다. 사용자는 모터 전원을 껐거나 분리했다고 확인했습니다. 이번 확인에서는 모터 구동 명령·서보 조향 시험·펌웨어 재업로드를 수행하지 않았으며, 전압·전류·회전·실물 정지는 미측정입니다. 접속/종료 시 기존 코드의 서보 중앙 명령은 적용됩니다.

현재 메인 스케치를 **Arduino SAMD 1.8.14 / Servo 1.3.0 / WiFiNINA 2.1.1 / Arduino_SpiNINA 0.0.2**로 컴파일해 성공했습니다(Flash 53,060 바이트, RAM 4,560 바이트). Python 3.11.4에서 조종기 문법과 도움말 실행도 확인했습니다. 처음 샌드박스 안의 UDP 검색은 응답을 받지 못했고 컴파일러는 Windows DLL 오류로 실행되지 않았으나, 실제 PC 환경에서 두 작업 모두 성공했습니다. 이 초기 실패는 보드 고장이나 라이브러리 미설치의 근거가 아닙니다.

현재 연결과 배선·키 사용법은 [실행 안내](../vehicle/manual_control/guide.ko.md)에 정리했고, `run_wifi_control.cmd`를 더블 클릭하면 메인 폴더의 Python 조종기가 실행됩니다. 기존 README/WIRING/PROJECT_OVERVIEW 파일은 작업 시작 때 삭제 상태였으므로 복원하거나 이전 MAI 배선을 재적용하지 않았습니다. 현재 보드가 L298N용 상태를 응답해 접속을 위한 재업로드는 필요하지 않았습니다.

사용자 조작용 명령 프롬프트 창에서 `wifi_control.py --host 192.168.50.222`를 실행했고, 해당 Python 프로세스가 Nano TCP 5000에 `Established` 상태로 연결된 것을 확인했습니다. 구동 키 입력은 수행하지 않았습니다.

## 이전 개발 기록

별도 `Dynamixel_Control`에 XM430-W210-T용 PC Python 속도 제어 예제를 추가했습니다. 사용자 지정 COM18과 첨부 위자드 화면의 ID 1·1 Mbps를 사용하고, XM430 주소와 Protocol 2.0을 적용합니다. 문법·가짜 통신 객체 검증 범위와 실물 시험을 구분하며, 모델의 실제 연결·회전·정지·watchdog 단절 시험은 미완료입니다.

3초 회전 `wheel_test.py`와 10초 위치·속도·각속도 출력 `wheel_monitor.py`, 각각의 Windows 실행 배치를 추가했습니다. 로컬 `.venv`에 SDK 4.1.0·pyserial 3.5를 설치하고 추가 테스트 9건·의존성 검사를 통과했습니다. 실제 SDK의 읽기 전용 PING은 COM18·1 Mbps·Protocol 2.0에서 ID 1과 7 모두 응답이 없었으며, 설정 쓰기·회전은 실행하지 않았습니다.

문서 기준일: **2026-09-30 (한국 시간)**. 현재 코드와 기존 시험 기록을 기준으로 정리했습니다. 문서·복제본 갱신은 추가 실물 시험이나 펌웨어 재업로드를 뜻하지 않습니다.

## 현재 개발 방향

아래는 중앙 후륜을 사용하던 2026년 10월의 배선과 시험 기록입니다. 현 차량의 좌우 독립 후륜 구성과 보정 상태는 [듀얼 후륜 구동](../README.md#듀얼-후륜-구동)에서 확인합니다.

**현재 실제 드라이버는 L298N이며 모터는 OUT1/OUT2에 연결돼 있습니다(2026-10-05 사용자 확인).** 사용자는 LED ON/OFF 성공과 `W/S`에도 모터가 돌지 않는 증상, ENB를 GND에 연결했다는 상태를 보고했습니다. 기존 MAI 코드의 D3 LOW 활성 ENABLE을 제거하고 메인 스케치를 **D9→ENA PWM, D2→IN1, D4→IN2, D3 미사용**으로 수정해 컴파일에 성공했습니다. 사용자 제공 `STATUS driver=L298N channel=A duty_cmd=-100.0% duty_applied=100.0% enabled=1`로 L298N용 펌웨어의 실행과 역방향 100% 소프트웨어 출력 상태를 확인했습니다. 모터는 반응하지 않았으며 실제 전압·전류·회전은 미검증입니다. ENA/ENB 두 핀 중 신호핀과 5 V 점퍼 핀을 식별하고, EN 점퍼 제거·현재 신호선·로직/모터 전원을 확인해야 합니다. ENB→GND도 ENB 신호핀인 경우에만 맞습니다.

**2026-10-05 실물 시험 결과(사용자 보고): 무선 연결로 서보 조향이 됩니다.** 앞서 서보에 5 V 전원을 연결했다고 보고했으며, 이번 조향 성공의 상세 전원 구성·조작 키·응답 로그는 미확인입니다. 기본 무선 조향 성공을 기록하고, 서보별 중앙·방향·기구 한계와 모터 구동은 별도 검증 항목으로 둡니다.

기존 메인 코드의 `PING` 내장 LED 시험은 [수동 조종기 키 목록](../vehicle/manual_control/guide.ko.md#조종기-실행)에 있습니다. 현재 코드의 접속·종료 처리는 서보 중앙 명령도 포함합니다.

2026-10-05에 기존 메인 스케치 컴파일, Python 문법 검사, USB Nano(COM6) 식별, 실제 UDP 응답 `192.168.50.222`와 PC/설정 SSID 일치를 확인했습니다. 이 준비 확인에서는 업로드·리셋·TCP 접속·LED 명령은 수행하지 않았습니다. 이후 LED ON/OFF 성공은 사용자 보고로 기록하며, 실물 배선 분리 여부와 정확한 응답 로그는 미확인입니다. L298N 구동 성공은 아직 확인되지 않았습니다.

**Nano 33 IoT 한 대 + 기존 공유기 Wi-Fi + 노트북 Python 조종기**로 중앙 후륜 DC 모터 1개와 앞바퀴 조향 서보 2개를 제어합니다. 현재 모터 드라이버는 L298N의 **A 채널(OUT1/OUT2)**을 사용합니다. 기존 MAI R 채널 및 Uno L 채널 설정은 과거 참고 기록입니다.

## 완료 기록과 미완료 항목

사용자는 L298N에 별도 12 V 전원을 연결했다고 보고했고, `5V_EN`이 없다는 말은 보드에 그 글자가 보이지 않는다는 뜻이라고 설명했습니다. 전원장치 사양, 레귤레이터 유무와 전원 점퍼 위치는 미확인입니다. `5V_EN`은 앞서 일반 모듈의 전원 점퍼 기능을 설명한 명칭이며 실물에 같은 표기가 반드시 있는 것은 아닙니다. 보드 전체와 전원 단자 주변 사진으로 모듈을 식별한 뒤 전원 공급 방식을 확정합니다.

**2026-10-05 추가 전원 관찰(사용자 보고):** 12 V를 연결했을 때 L298N의 불이 꺼져 있고, 드라이버의 `5V` 단자에 외부 5 V를 연결했을 때 불이 켜졌습니다. **같은 날 사용자 측정: 12 V 공급 상태에서 드라이버 `12V` 단자–GND는 12 V, `5V` 단자–GND는 0 V입니다.** 로직 5 V가 공급되지 않는 상태가 확인됐습니다. 정확한 모듈·전원 점퍼 구성은 미확인이므로, 레귤레이터가 비활성화된 경우와 레귤레이터 경로 고장은 아직 구분되지 않았습니다. ENA/ENB 점퍼와 전원 점퍼는 별개이며, 모듈 구성을 확인하기 전에는 내부 레귤레이터와 외부 5 V를 함께 사용하지 않습니다. 외부 5 V에서 LED가 켜져도 레귤레이터나 모터 출력부의 정상 동작까지 입증되지는 않습니다.

**2026-10-05 사용자 제공 진단:** L298N A 채널 STATUS 응답에서 `duty_cmd=-100.0%`, `duty_applied=100.0%`, `enabled=1`인데 모터가 반응하지 않았습니다. 먼저 `X`로 정지한 뒤 모터 전원 단자–GND, 로직 5 V 단자–GND 전압과 Nano–L298N 공통 GND를 확인합니다. 이 STATUS는 명령 상태이며 ENA/IN/OUT 전압 실측을 대신하지 않습니다. 설치된 Nano D9의 PWM은 TCC0, Servo 1.3.0은 TC4를 사용하므로 소스 설정상 직접 타이머 충돌은 발견되지 않았습니다.

**2026-09-30 기록된 무동력 시험:** R 채널 스케치를 Arduino SAMD 1.8.14로 컴파일·업로드했습니다. 실제 Nano에서 UDP 검색, TCP `STATUS`/`NETWORK`/`PING`/`IDLE` 왕복, 2초 이상 명령 없이 소프트웨어 출력 상태 유지, `STOP` 후 소프트웨어 정지 상태를 확인했습니다.

**아직 확인되지 않은 부분:** L298N ENA/ENB의 정확한 핀·점퍼·전원과 실제 Nano 신호선, 수정 펌웨어 업로드, 드라이버 출력 전압·모터 회전, 서보별 중앙·방향·기구 한계, 모터/전원 정격, 전류·발열, 연결 해제 시 실물 정지입니다. 기본 서보 무선 조향은 사용자 보고로 성공했으며, `enabled=0/1`이나 `OK DRIVE`는 코드 상태·명령 응답으로 모터 실물 동작의 증거가 아닙니다.

**현재 구성의 한계:** Nano가 리셋되거나 USB 전원이 사라지는 동안 ENA 상태를 코드로 보장할 수 없습니다. 모터 전원을 분리한 상태에서 리셋 중 핀 상태와 ENA 풀다운 구성을 확인하고, 모터 전원의 물리 차단 수단을 준비합니다. 현재 구성의 지면 주행은 검증되지 않았습니다.

| 1 | 전원 구성 | 배터리/전원장치·DC-DC 모델, 출력 전압과 공급 가능 전류, 모터/로직/서보/Nano 분기와 공통 GND, 차단 스위치·퓨즈 | 로직·서보 전원 누락과 전류 용량 확인 |
| 2 | 무동력 신호 측정 | 로직 5 V 공급·전원 LED, 정지 시 ENA LOW, 구동 명령 시 ENA PWM과 IN1/IN2 상태, 모듈 GND와 Nano GND | 코드 응답과 실제 드라이버 입력 상태를 구분 |
| 2 | 서보와 차체 보정 | 실제 서보 모델, D5/D6가 움직이는 바퀴, 중앙 펄스·회전 방향·기구 한계, 축간 거리와 앞바퀴 간격 | 기존 교차 채널·중앙값·조향 계산 설정의 적합성 확인 |

현재 코드의 차체 설정은 도면 기반 명목 축간거리 **133.24 mm**, 조향 회전축 간격 **121.20 mm**, 서보 채널 L/R(D5/D6) 중앙 **1597/1416 µs**, 방향 **+1/+1**, 펄스 범위 **948~1948/952~1952 µs**입니다. 중앙 펄스는 위 2026-10-08 2차 정렬 관찰에서 계산했고 이후 사용자 보고로 중립 성공을 확인했습니다. 방향은 후속 요청에 따라 D6만 반전했습니다. 치수 산출 가정은 문서 첫 항목에 기록했으며 실측은 아닙니다. 바퀴 각도 설정 한계 **-45°~+55°**와 펄스 한계를 함께 적용한 중심 각도 계산 범위는 약 **-34.50°~+39.99°**이고, 키보드 명령 범위는 **-30°~+30°**입니다. 실제 기구의 허용 범위와 명령 대비 바퀴 각도는 별도로 확인해야 합니다.

모터 전원 투입 전 확인은 [현재 배선 문서](../vehicle/firmware/wiring.ko.md)를 따릅니다. 모터 정지 전류는 우선 제조사 자료로 확인하며, 확인을 위해 임의로 모터를 잠가 시험하지 않습니다. `DRIVE`의 7 V 보정 때문에 최초 벤치 시험은 `MOTOR 5` 같은 낮은 PWM 명령부터 시작하도록 문서화돼 있습니다.

통신이 다시 실패할 때는 시리얼 `READY`와 `STATUS`/`NETWORK`/`PING` 응답, 증상과 발생 시점을 기록합니다. Wi-Fi 비밀번호는 공유할 필요가 없습니다.

## 다음 작업 순서

먼저 L298N의 ENA/ENB 신호핀과 점퍼, 현재 전원을 확인하고 새 코드의 D9/IN1/IN2 연결에 맞춥니다. 그다음 모터 전원을 분리한 상태에서 수정 펌웨어를 업로드합니다. LED ON/OFF는 기존 코드에서 사용자 보고로 성공했으며, 새 코드의 모터 시험은 아직 남아 있습니다.

Wi-Fi 모듈 자체나 공유기 접속을 따로 진단해야 할 때 사용할 수 있는 [springmaru 진단 스케치](../reference/springmaru_poweron_nano33_iot/README.md)를 별도 참고 자료로 보관했습니다. NINA 펌웨어 버전·MAC·주변 SSID·암호화 방식 표시와 HTTP 8000 연결 시험을 제공합니다. 현재 차량 펌웨어에 합치지는 않았으며, 이 진단 스케치의 실물 시험은 이번 정리 작업에서 수행하지 않았습니다. 차량 구동부를 분리한 별도 시험과 메인 스케치 복귀 절차는 해당 안내를 따릅니다.

1. 모터 라벨·드라이버 하네스·전원 사양을 확인해 위 미확인 항목을 채웁니다.
2. L298N A 채널 배선과 EN 점퍼를 확인하고, 모터 전원을 분리한 상태에서 새 코드를 업로드해 로직 5 V와 ENA 정지 LOW를 확인합니다.
3. 서보 중앙·방향·기구 한계를 확인하고 현재 코드의 보정값과 비교합니다.
4. 모터·드라이버 적합성과 신호 조건을 확인한 뒤 바퀴를 띄워 짧게 구동·정지·연결 해제를 시험하고 결과를 기록합니다.
5. 지면 주행이 목표라면 리셋·전원 손실 중 정지 한계를 해결한 후 완료 기준을 다시 정합니다.

## 파일 버전 관리 기준

**현재 개발 원본은 `C:\Users\user\Arduino\Nano_33_IoT`입니다.** 기존 junction을 별도 이름으로 보존하고 필요한 파일을 복제해 만든 독립 폴더입니다. 현재 Nano 코드와 조종기는 `vehicle/`에, 기존 Uno 자료는 [reference/Uno_Single_Rear_Motor](../reference/Uno_Single_Rear_Motor/README.md)에 있습니다. 프로젝트 진입점은 [README.md](../README.md)입니다.

이전 `C:\Users\user\Arduino\PowerOn`과 OneDrive PowerOn 폴더는 이전 작업 내용을 보존한 사본입니다. 현재 수정·실행·업로드는 메인 폴더를 기준으로 하며 이전 사본의 자동 동기화는 구성돼 있지 않습니다. 기존 `.git` 이력과 과거 백업은 원래 위치에 보존했습니다. Wi-Fi 설정은 로컬 사용을 위해 복제했으며 `.gitignore`에서 제외하고 공개 자료에는 포함하지 않습니다.

기존 Uno의 L 채널·1.5초 감시 설명은 그 코드에 맞는 참고 정보입니다. 현재 Nano는 L298N A 채널을 대상으로 하며, 과거 MAI R 채널 시험을 현재 모터의 구동 검증으로 바꾸지 않습니다. 새 측정이나 시험을 완료했을 때만 날짜·조건·결과를 기록하고 관련 완료 표시를 갱신합니다.
